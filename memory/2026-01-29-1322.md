### **📂 WORKSPACE DESCRIPTIONS**

#### **1. PDF PROCESSOR** (`pdf-processor`)
- **Co robi:** Konwertuje pliki PDF do Markdown używając Docling OCR.
- **Input:** Plik PDF (ścieżka).
- **Output:** JSON z pełnym markdown (26850 znaków typowo).
- **RAM Usage:** ~750 MB (Docling + processing).
- **Czas:** ~5s na PDF.

#### **2. SECTION 3 EXTRACTOR** (`section3-extractor`)
- **Co robi:** Wybiera Sekcje 3 (Composition/Ingredients) z pełnego markdown.
- **Input:** JSON z pełnym markdown.
- **Output:** JSON z sekcją 3 (tylko kompozycje, ~2000 znaków typowo).
- **Metoda:** Regex patterns (headings: "SECTION III", "Section 3", etc.).
- **RAM Usage:** ~50 MB (parsing stringów).
- **Czas:** ~1s na PDF.

#### **3. LLM EXTRACTOR** (`llm-extractor`)
- **Co robi:** Wyciąga substancje chemiczne z Sekcji 3 używając LLM (dynamiczne dane).
- **Input:** JSON z sekcją 3 (skróconą).
- **Output:** JSON z listą substancji (name, CAS, percentage).
- **Metoda:** LLM (Qwen3-VL-8B-Instruct-MLX) przez LM Studio.
- **RAM Usage:** ~60 MB (LLM client + processing).
- **Czas:** ~40s na PDF.

#### **4. PUBCHEM ENRICHER** (`pubchem-enricher`)
- **Co robi:** Wzbogaca substancje o dodatkowe dane z PubChem API.
- **Input:** JSON z listą substancji (name, CAS).
- **Output:** JSON z listą substancji (CID, molecular_formula, etc.).
- **Metoda:** HTTP GET do `pubchem.ncbi.nlm.nih.gov` per substancja.
- **RAM Usage:** ~10 MB (HTTP requests).
- **Czas:** ~1s na 10 substancji.

#### **5. REGULATIONS CHECKER** (`regulations-checker`)
- **Co robi:** Sprawdza, czy substancje są regulowane (toxic, hazardous, etc.).
- **Input:** JSON z listą substancji (enriched).
- **Output:** JSON z listą substancji (is_regulated, etc.).
- **Metoda:** SQLite DB lookup (`substances_regulation.db`).
- **RAM Usage:** ~5 MB (SQL queries).
- **Czas:** <1s na 10 substancji.

#### **6. PIPELINE COORDINATOR** (`pipeline-coordinator`)
- **Co robi:** Orchestruje wszystkie workspace'y w sekwencji (jeden PDF po drugim).
- **Input:** Lista PDFs (lub pojedynczy PDF).
- **Output:** JSON per PDF + `pipeline_summary.json` + `pipeline_summary.csv`.
- **Metoda:** `subprocess.run` z JSON piping przez `stdin`/`stdout`.
- **RAM Usage:** ~100 MB (monitoring + koordynacja).
- **Czas:** ~50s na PDF (cały pipeline).

### **💡 ZALETY TEGO PODEJŚCIA**

1. **Izolacja Błędów:**
   - Jeśli `llm-extractor` zawiedzi, `pdf-processor` i `section3-extractor` są gotowe.
   - Nie ma propagacji błędów przez cały pipeline.

2. **Wydajność RAM:**
   - Każdy workspace używa własną pamięć i zwalnia ją po zakończeniu.
   - Maksymalne zużycie RAM = max(workspace RAM) + koordynacja.
   - Unikamy SIGKILL na poziomie systemu (chyba że pojedynczy workspace używa >16GB).

3. **Parallel Processing (Opcjonalne):**
   - Można uruchomić 5 PDFs równolegle (każdy w osobnym terminalu).
   - Zysk: ~5x przyspieszenie (44s/PDF → ~9s/PDF).
   - Wymagania: 5 terminali lub `concurrent.futures.ThreadPoolExecutor`.

4. **Monitorowanie Systemu:**
   - `pipeline-coordinator` monitoruje RAM/CPU po każdym PDF (`psutil`).
   - Wypisuje logi: `[3/10 PDFs] RAM: 7500/16384 MB (45.8%), CPU: 1.0%`.
   - Można zidentyfikować, który PDF powoduje wyciek pamięci.

5. **Elastyczność:**
   - Można podmienić LLM (np. z Qwen3 na GPT-4o) zmieniając tylko `llm-extractor/pyproject.toml`.
